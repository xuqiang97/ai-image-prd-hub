## 业务背景和价值

美工版、运营版均已上线独立的“查看已完成生图”页面，页面根据当前登录用户的数据权限生成创建人树，并按创建人查询已完成任务和图片。

员工离职后，业务仍可能需要回查其历史作图记录，用于素材复用、问题追溯和团队工作承接。当前普通上级及特殊管理团队无法按现有权限继续查看这些历史记录，仅系统级管理员可通过当前业务端全量权限查看，影响历史成果的持续使用。

如果默认把权限范围内持续累积的全部离职员工 ID加入每次查询，会增加查询参数和数据库压力；组织系统中还存在大量从未使用过 AI生图系统的离职员工，直接全部展示也会增加无效数据。因此，本期保持默认只查询在职员工，仅向用户提供当前权限范围内、确实存在已完成生图任务的离职员工，并在用户主动勾选后查询其历史记录。

## 需求概述

1. 美工版、运营版“查看已完成生图”的创建人树均支持展示和选择离职员工。
2. 页面首次进入及重置后，创建人默认值仍为当前用户权限范围内的全部在职员工，离职员工默认不选中、不参与查询。
3. 在职员工继续按现有权限树展示；离职员工仅保留在当前业务端存在至少一条有效“已完成生图”任务的人员。
4. 同一组织节点内，在职员工排列在前，离职员工排列在最后；后端返回 `isActive=false` 时，姓名直接显示为灰色。
5. 用户可以展开组织树或使用现有搜索能力找到离职员工，主动勾选后查询其历史记录。
6. 当前角色、组织范围、特殊团队权限、父子节点级联选择及其他查询条件继续沿用现状。

本需求只调整现有创建人树的数据范围、默认选择、人员排序、状态样式和查询权限，不新增页面、弹窗或复杂交互，不需要单独制作 HTML原型。

## 功能需求

### 1. 影响入口和改造范围

| 业务端 | 页面 | 直接改造范围 |
|---|---|---|
| 美工版 | 查看已完成生图（美工版） | 创建人树及搜索、创建人默认值、美工版创建人及任务查询链路 |
| 运营版 | 查看已完成生图（运营版） | 创建人树及搜索、创建人默认值、运营版创建人及任务查询链路 |

美工版、运营版两个实际页面入口必须遵循相同的人员状态、默认选择、展示和权限规则。研发需先确认创建人接口、树形组件和列表查询逻辑在两版及其他页面中的真实复用关系：共享逻辑只改造一次，并将全部实际调用入口列入回归范围；独立实现则分别改造和验收。其他调用页面不需要展示离职员工时，不得因共享接口或组件改造而被动扩大人员范围。

现有状态子 Tab、时间、任务图张数、普通与批量搜索、图片筛选、排序、展示密度、任务分页、列表卡片、查询、重置及 L3只读查看继续沿用现状。

### 2. 人员状态和离职人员范围

创建人接口的每个人员对象返回非空布尔字段 `isActive`：

| `isActive` | 人员状态 | 本期处理 |
|---|---|---|
| `true` | 在职 | 沿用现有权限树、展示、默认选择和查询规则 |
| `false` | 离职 | 按本期离职人员范围、排序、样式和主动选择规则处理 |

正常人员对象必须返回 `isActive`，不得缺失、返回 `null` 或使用字符串代替布尔值。字段异常时，前端不得根据姓名、组织节点或其他字段自行推断人员状态，接口异常处理沿用现有创建人树规则。

离职员工可展示范围定义为：

```text
当前业务端可展示离职员工
= 当前登录用户按现有角色计算出的当前业务端可见组织范围内、isActive=false 的人员
∩ 当前业务端存在至少一条有效“已完成生图”任务的创建人
```

具体规则：

1. “有已完成任务”复用当前“查看已完成生图”页面对任务完成状态、有效记录及删除状态的现有判断，不另建一套完成口径。
2. 判断离职员工是否需要出现在创建人树时，检查其在当前业务端的全部历史有效已完成任务，不受页面当前时间、模型、图片类型、状态子 Tab等筛选条件影响。
3. 美工版只根据美工版任务判断，运营版只根据运营版任务判断；一个用户在某一业务端没有已完成任务时，不得因其在另一业务端有任务而出现在当前页面。
4. 从未使用过当前业务端、只有未完成或无效任务的离职员工，不展示且搜索不到。
5. 上述“有已完成任务”限制只用于离职员工；在职员工继续按当前权限树展示，不要求必须已有完成任务。
6. 同一人员按稳定创建人 ID去重，不因存在多条历史任务而重复展示。

### 3. 默认选择和查询

1. 页面首次进入时，创建人默认选择当前登录用户在当前业务端权限范围内的全部在职员工。
2. 离职员工即使出现在创建人树中，也一律不默认选中，不参与首次查询。
3. 创建人可选择集合包含当前权限范围内的全部在职员工和符合第2节条件的离职员工；默认查询集合只包含当前权限范围内的全部在职员工。可选择集合不得直接等同于默认查询集合。
4. 页面重置后，创建人恢复为当前权限范围内的全部在职员工，清除用户手动选择的离职员工。
5. 页面首次进入、重置，或创建人请求未明确包含离职员工 ID时，离职员工不得参与查询。现有接口如将“未传创建人条件”解释为“全部可选择创建人”，本期必须通过前端显式提交默认在职员工集合，或调整后端默认解释规则，确保默认结果只包含在职员工；具体实现由研发选择。
6. 默认查询不得为了支持本需求而携带当前权限范围内全部离职员工 ID。
7. 用户主动勾选一个或多个离职员工后，对应创建人 ID才加入本次查询；取消勾选后不再参与后续查询。
8. 选择离职员工后，时间、任务维度、图片维度及其他现有条件继续共同生效。离职员工存在历史任务但不在当前时间范围内时，列表可以为空；用户调整时间范围覆盖历史任务后方可查询到。
9. 在职员工和用户主动选择的离职员工可以同时作为创建人条件查询；本期不新增“仅看离职员工”开关。

### 4. 创建人树、排序和样式

1. 创建人继续使用现有组织树结构，现有部门、组及人员层级不变。
2. 符合条件的离职员工直接显示在现有组织归属节点下，不新增独立的“离职人员”部门或分组节点。
3. 同一直属组织节点内，在职员工排列在前，离职员工统一排列在最后；在职员工之间、离职员工之间分别沿用现有人员排序规则。
4. `isActive=false` 时，只将人员姓名显示为清晰可读的中性灰色；复选框、悬停、勾选等交互保持可用，不得显示为禁用状态。
5. 组织节点的父子级联勾选继续沿用现有组件行为，不针对离职员工增加特殊的排除、限制或批量选择规则。
6. 页面首次进入及重置后，在职员工全部选中、离职员工未选中；组织父节点的选中或半选状态根据子节点实际选择结果沿用现有级联组件展示，不为保持父节点全选状态而自动选中离职员工。
7. 某组织节点没有符合条件的离职员工时，不增加空节点或占位文案。

### 5. 创建人搜索

1. 创建人树继续保留现有搜索能力，匹配字段、匹配方式、输入处理和结果选择方式均不改变。
2. 搜索范围同时包含当前权限范围内的在职员工和符合第2节条件的离职员工。
3. 离职员工无需先输入关键字才进入数据范围；用户既可以展开组织树查找，也可以输入现有支持的关键字搜索。
4. 搜索结果中的人员继续遵循在职在前、离职在后的排序，离职员工姓名显示为灰色。
5. 无权限的离职员工及没有当前业务端已完成任务的离职员工，不得通过搜索暴露姓名或被选择。

### 6. 数据权限

本期不新增角色或重定义现有组织权限，只在各角色当前可见组织范围内补充符合条件的离职员工：

1. 本期沿用现有权限优先级：系统级管理员 > 特殊团队或特殊人员 > 默认岗位层级。一个用户同时命中多个角色时，采用最高优先级对应的可见组织范围，再在该范围内计算符合条件的离职员工集合；不得对多个角色范围取交集而缩小权限，也不得跨当前业务端扩大权限。
2. 普通上级继续按现有组、部门等权限范围查看在职和离职员工，不得跨无权限组织查看。
3. 深圳亚马逊业务管理部继续按当前权限范围查看深圳运营数据；成都 FBA策略管理组、成都 FBM策略管理组继续分别按当前权限范围查看成都 FBA部门、成都 FBM部门数据。特殊团队的现有可见组织范围用于计算本期离职员工集合。
4. 系统级管理员在当前页面的可见组织范围为当前业务端全体，但美工版和运营版仍不得跨数据域混查。
5. 创建人树、搜索结果、默认选择和列表查询必须使用同一套后端权限结果，不能只在前端隐藏无权限人员。
6. 用户提交的离职员工 ID必须属于其当前业务端可展示离职员工集合；伪造或提交无权限创建人 ID时，沿用现有越权请求处理且不得返回无权限任务或图片。
7. 本期直接沿用现有组织系统返回的人员组织归属。组织冗余、离职人员归属错误、历史调岗组织拆分及按任务创建时组织还原不在本期处理。
8. 历史任务只保存稳定创建人 ID，没有保存任务创建时组织。离职员工按现有组织归属获得查看权限后，当前有权用户可以查看该员工在当前业务端符合时间及其他筛选条件的全部历史已完成任务，本期不能按该员工历史任职组织拆分任务。
9. 提测前按现网权限配置或权限负责人确认当前仍有效的完整角色清单；仍有效的普通上级、特殊团队和管理角色均纳入回归，已下线或已改名的历史角色不因本需求重新加入权限范围。

### 7. 状态变化

1. 在职员工变为离职后，页面下次重新加载创建人数据时按最新 `isActive=false` 处理。
2. 该员工在当前业务端有有效已完成任务时，移动至所属节点人员列表最后、姓名显示为灰色且不再默认选中；没有有效已完成任务时不再展示。
3. 离职员工重新变为在职后，页面下次重新加载时按在职员工规则排序和默认选择。
4. 页面已经打开期间不要求实时监听人员状态变化；刷新页面或重新加载创建人数据后必须生效。

### 8. 数据获取和性能要求

1. 后端创建人接口应直接返回当前权限范围内的在职员工，以及满足“当前业务端存在有效已完成任务”条件的离职员工；不得把全部离职员工返回前端后再过滤。
2. 默认列表查询只使用默认选中的在职员工，不得因本需求默认追加全部离职员工 ID。
3. 用户主动选择离职员工后，列表查询只追加本次实际选中的离职员工 ID，不得自动扩大到同组织全部离职员工。
4. 研发根据现有数据表、索引和接口实现选择集合查询、关联、索引或缓存方案，但必须保证创建人树和列表查询结果符合本文规则。
5. 提测前分别使用美工版、运营版离职人员较多的实际权限范围核对创建人树加载、搜索和查询表现。默认不选择离职员工时，创建人树和列表查询必须在接口现有超时阈值内正常返回，不得出现超时、5xx或服务异常；测试需记录改造前后同条件响应耗时，发现差异影响现有使用时由研发在提测前完成查询优化。
6. 父节点级联选择可能一次带入较多人员，继续沿用现有组件行为；研发需按现有接口超时和稳定性要求验证该场景，不在本需求中新增选择人数上限。
7. 提测前按实际接口分别更新现有接口文档，写清 `isActive` 的响应层级、布尔类型、必返和非空要求，补充离职员工返回范围、当前业务端隔离、默认查询及主动选择后的请求和响应示例；共享接口还需列明全部调用方及兼容范围。

### 9. 本期边界

- 不新增或调整左侧菜单、页面路由、状态子 Tab、筛选分区、任务与图片卡片、分页器及 L3沉浸式大屏。
- 不修改 AI生图任务创建、编辑、审核、推送、复制重跑及其他未列明页面的权限。
- 不新增“离职人员”分组、“仅看离职员工”开关、提示弹窗或新的搜索字段。
- 不新增任务创建时组织字段，不回刷历史任务组织，不还原员工历史调岗关系。
- 不处理现有组织系统中的冗余部门、人员重复归属或归属错误；相关问题后续作为独立需求处理。
- 不改变在职员工现有展示范围、排序、搜索匹配、父子级联选择及数据权限。

## 风险描述

| 风险 | 处理方式 |
|---|---|
| 现有组织归属存在冗余或错误，可能影响离职员工出现的节点和可见范围 | 本期以现有组织系统归属为准，不在任务数据中推断组织；组织治理后续拆分独立需求。 |
| 历史任务没有创建时组织，同一离职员工可能曾跨部门任职 | 本期按现有组织归属授权；获得权限后可查看该员工在当前业务端符合筛选条件的全部历史已完成任务，无法按历史任职组织拆分，组织历史治理后续单独处理。 |
| 两版入口及其共享或独立逻辑的复用关系不清，可能造成重复改造、漏改调用方或规则不一致 | 研发先确认真实复用关系；共享逻辑改造一次并回归全部调用入口，独立逻辑分别改造，美工版、运营版使用同一验收集核对。 |
| 如果后端返回全部离职员工再由前端过滤，无法达到减少数据量的目标 | 后端按权限及当前业务端有效已完成任务先行过滤，只返回符合条件的离职员工。 |
| 父节点级联选择可能带入较多离职员工，增加单次查询量 | 沿用现有组件行为，在离职人员较多的实际范围完成稳定性验证，不默认携带离职员工。 |
| `isActive` 缺失或类型不一致导致人员状态判断错误 | 接口统一返回非空布尔值，前端不自行推断。 |

## 验收标准

| # | 验收场景 | 预期结果 |
|---:|---|---|
| 1 | 分别首次进入美工版、运营版查看已完成生图 | 创建人默认选择当前登录用户在当前业务端权限范围内的全部在职员工，离职员工均未选中，首次查询不携带离职员工 ID；组织父节点按子节点实际选择结果显示选中或半选状态，不自动选中离职员工。 |
| 2 | 修改创建人条件后执行页面重置 | 两版均恢复为当前权限范围内的全部在职员工，手动选择的离职员工被清除。 |
| 3 | 同一组织节点内同时存在在职员工和有当前业务端已完成任务的离职员工 | 在职员工在前、离职员工在最后；离职员工姓名为可读灰色，复选框和选择交互可用。 |
